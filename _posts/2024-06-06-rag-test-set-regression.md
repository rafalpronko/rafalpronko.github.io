# Building a RAG Test Set: Questions, References, and Regression Reports

![Diagram: a versioned test set and two stored runs are paired by case ID. Two cases are fixed and two regress, so the overall pass count is 8/10 for both runs, but one regression is critical and the release gate fails.]({{ '/assets/images/rag-test-set-regression.svg' | relative_url }})

<time datetime="2024-06-06">6 June 2024</time>

A change to a RAG system rarely makes everything better or everything worse. A new chunking strategy helps one kind of question and hurts another. A new prompt makes the model more willing to answer — including questions it should refuse.

If the only number I look at is "accuracy went from 80% to 80%", I learn nothing. Worse, I may ship a change that broke the one question that matters most, because two unimportant questions improved at the same time.

In this article I build two things: a small RAG test set with explicit references, and a regression report that compares two runs case by case. The report is designed so that a single regression cannot hide behind an aggregate that stayed the same.

## What this example is, and what it is not

Retrieval-augmented generation combines a retriever, which finds passages, with a generator, which writes the answer from them. The original RAG paper describes exactly this split between retrieval and generation. That split is the reason a RAG test case needs more than a question and an expected answer: I also want to know which passages should support the answer.

The example is an **offline regression evaluator of stored responses**. It does not call a language model and it does not run a retriever. It reads:

- a synthetic corpus of passages with stable IDs,
- a versioned test set,
- two files of responses that a system produced earlier — `baseline.json` and `candidate.json`,
- a gate policy with thresholds.

Everything is synthetic. "Tidepool" is a product I made up so that the corpus has something to describe. The responses were written by hand to create specific situations, not generated by a real system. Nothing here measures how good any model or retriever is.

That is deliberate. Once responses are stored, scoring is deterministic and cheap, so I can test the evaluator itself — including how it reacts to broken input. Generating the responses is a separate step with its own costs and randomness.

## What a test case contains

Here is one case from the example test set:

```json
{
  "case_id": "q-sso-plan-role", "group_id": "g-sso", "split": "holdout",
  "kind": "multi_hop", "critical": true,
  "question": "Which plan and which role do I need to set up SAML single sign-on?",
  "expected_behavior": "answer", "required_facts": ["enterprise", "owner"],
  "evidence_sets": [["P-sso-plan", "P-sso-role"]]
}
```

Every field answers a question I would otherwise argue about after the fact:

- `case_id` — a stable identifier. Results are compared by this ID, never by list position or question text.
- `group_id` — which cases are variants of the same underlying question. It controls the dev/holdout split.
- `split` — `dev` for iterating on the system, `holdout` for release decisions.
- `kind` — a slice label: `single`, `paraphrase`, `multi_hop`, `time_scoped`, `ambiguous`, `unanswerable`.
- `critical` — whether a failure on this case blocks a release on its own.
- `expected_behavior` — `answer`, `abstain` or `clarify`.
- `required_facts` — short strings that a correct answer must contain.
- `evidence_sets` — which passages together justify the answer.

The test set itself has a `dataset_version` and the `corpus_version` it was written against. Both matter later.

## Choosing questions: representative, not just convenient

The easiest test set to write is the one where I open the documentation, pick a sentence and turn it into a question. Such a set mostly measures whether the system can find a sentence that matches the question word for word.

Questions should look like the ones the system will actually receive. If I have access to real queries and permission to use them, I sample from them and stratify by topic and type, so that rare but important kinds of question are not drowned out by the common ones. If I don't, I write questions deliberately across the categories I care about and say clearly that the distribution is my assumption.

In both cases I record the slice of each question. A total pass rate over a set that is 90% simple lookups says little about multi-hop questions. Slices make this visible, but they also make a different problem visible: a slice with two cases is not a measurement, it is an anecdote. In the example, `multi_hop` has one case. That is fine for a demonstration of the mechanics and not fine for a real decision.

## Answerable, unanswerable and ambiguous questions

A RAG system that answers every question confidently is not a good system. Some questions have no answer in the corpus. "Is Tidepool HIPAA certified?" is one of them: no passage mentions it. The correct behaviour is to abstain, not to guess.

So `expected_behavior` is part of the reference. In the example there are three values:

- `answer` — the corpus supports an answer; facts and evidence are required.
- `abstain` — the corpus does not support an answer; any answer is a failure.
- `clarify` — the question is ambiguous. "What is the limit?" could refer to the API rate limit or the upload size limit; the corpus has both. A good response asks which one.

The validator enforces consistency: an `answer` case must have facts and evidence, and an `abstain` or `clarify` case must have neither. Otherwise I could accidentally write an unanswerable question that still "expects" some evidence, and nobody would notice.

Abstention has a cost on the other side too. A system that refuses everything would pass every unanswerable case. That is why abstaining on an answerable question counts as a failure, and why the pass rate uses all cases as its denominator — more on that below.

## Evidence sets and multi-hop questions

A single list of "relevant passage IDs" is not enough. Two situations break it.

**Multi-hop:** to say "Enterprise plan and the owner role" I need two passages — one about the plan, one about the role. Citing only one of them is not support for the full answer. So an evidence set is a list of passages that are needed *together*.

**Alternatives:** "How long does the Team plan keep audit logs?" can be justified by the plan description (`P-ret-team`) or by the changelog entry about the change (`P-change-team`). Either is enough. So a case has a list of evidence sets, and any one complete set counts.

In code, that is a single condition: the citations must contain at least one whole evidence set.

```python
if not any(set(es) <= cited for es in case["evidence_sets"]):
    reasons.append("citations cover no reference evidence set")
```

The test suite checks both directions: a partial multi-hop citation fails, and an alternative set is accepted.

## Paraphrases and leakage between dev and holdout

Paraphrases are useful. "How long are audit logs kept on the Enterprise plan?" and "For an Enterprise workspace, what is the audit log retention period?" test whether the system depends on exact wording.

They are also a leakage trap. If one version is in `dev` and the other in `holdout`, every prompt tweak I make while looking at the dev case is partly tuned to the holdout case. The holdout score then overstates how well the change generalises.

The fix is to split by **group**, not by case. All variants of the same underlying question share a `group_id`, and the validator rejects a group that appears in both splits:

```text
group 'g-logs' appears in both dev and holdout
```

The same reasoning applies to other channels. If I copy holdout questions into few-shot examples in the prompt, or write the questions from the exact passages I then use as examples, the split no longer protects me. Code can check groups; it cannot check what I pasted into a prompt. That needs discipline: develop on dev, look at holdout rarely, and when holdout has been used to make many decisions, refresh it.

## Time and version scope

Documentation changes. In the example corpus the Team plan retention changed from 30 to 90 days. A reference answer "90 days" is only correct for a specific version of the corpus.

So I pin the scope in three places:

1. The corpus has a `corpus_version`.
2. The test set records which `corpus_version` it was written against.
3. Each stored run records the dataset version and the corpus version it was produced with.

The validator rejects any mismatch. If someone re-indexes the corpus and runs the candidate on new documents while the baseline used old ones, the comparison is not a comparison of systems any more. It is a comparison of systems plus a data change.

Questions whose answer depends on time get the scope in the question itself: "According to the documentation as of 2024-05-01...". When the corpus changes, the dataset version should change too, and time-scoped references should be reviewed rather than silently carried over.

## Stable IDs and strict validation

The comparison is built on pairing: case `q-sso-plan-role` in the baseline against case `q-sso-plan-role` in the candidate. That only works if both runs answer exactly the same set of cases.

The validator rejects, with an error instead of a warning:

- duplicate `case_id` in the test set,
- evidence that points to a passage ID that does not exist in the corpus,
- a run with a missing response, an extra response or a duplicate response,
- a run whose `dataset_id`, `dataset_version` or `corpus_version` differs from the test set,
- unknown `action` values, wrong field sets, facts given as a string instead of a list,
- an empty test set or an empty run, and `null`, a list or an object where a list of cases or a string ID is expected,
- a gate policy whose thresholds have the wrong type or range: `true` instead of a count, `"0.5"` instead of a number, a negative limit.

There is one more trap below all of these. Python's `json` module, by default, does not reject an object with a repeated key — it keeps the last value. A response file with two `"answer"` keys would load without complaint. It also accepts `NaN` and `Infinity`, which are not valid JSON; a `NaN` threshold makes every comparison with it false, so the gate rule that uses it can never fail. The loader rejects both. For repeated keys it uses `object_pairs_hook`:

```python
def _reject_duplicate_keys(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValidationError(f"duplicate key {key!r}")
        result[key] = value
    return result
```

Why so strict? Because the alternatives are worse. If a missing case is skipped, the candidate's pass rate is computed over a different set than the baseline's. If a missing case is counted as a failure, a broken export looks like a model regression. Both give a number that looks meaningful and is not. An invalid input — including a missing or unreadable file — should stop the report with exit code 2, which is a different signal from "the gate failed" (exit code 1).

The order of the checks matters as well. The validator checks that an ID is a string before it looks the ID up in a set. Otherwise a list in that field raises `TypeError` inside the lookup, the program crashes with exit code 1, and a broken file looks exactly like a failed gate.

Writing the tests first paid off here. The test for facts given as a string (`"400 days"` instead of `["400 days"]`) failed with `DID NOT RAISE` on the first implementation: the scorer would have iterated over the characters of the string. The bug existed before the test; the test made it visible.

## What the scores do and do not prove

For an `answer` case, a response passes when:

1. its action is `answer`,
2. every required fact appears in the normalised answer text,
3. its citations contain at least one complete evidence set.

For `abstain` and `clarify` cases, a response passes when the action matches. The evaluator also computes evidence recall of the retrieved passages as a diagnostic; it is stored with each case score but not printed in the report, and retrieval is not part of pass/fail here.

These checks are **proxies**. They are cheap, deterministic and good at catching certain failures: a missing fact, a missing citation, an answer where there should have been an abstention. They are bad at the property I care about most — whether the answer is faithful to the evidence.

- "It is not 400 days" contains the fact `400 days` and passes.
- An answer can cite the right passage and still state something the passage does not say.
- The candidate's answer to the time-scoped question, "It was 30 days before the 2024-05-01 change; it is now 90 days", passes. Here that is correct, but the check would also pass a confused answer that mentions both numbers in the wrong order.
- Matching facts as substrings is brittle in the other direction: "3 times" does not contain `three`.

So a passing case means "no cheap check found a problem", not "the answer is correct". For faithfulness I need a reviewer — a person, or a model used as a judge with its own rubric and its own biases — and the reviewer's verdict should be stored alongside the run so that it can be compared just like the cheap checks. Frameworks such as Ragas propose reference-free metrics for these properties; I don't use one here, because the point of the example is the structure of the test set and the report, not a particular scoring method.

Rubrics have limits as well. A binary pass hides partial answers; a 1–5 score hides what was wrong. Whatever the scoring, I want the report to name the reason for each failure.

## Pairing per case, then aggregating per slice

The comparison has two steps. First, every case gets one of four outcomes:

- `kept_pass` — passed in both runs,
- `kept_fail` — failed in both runs,
- `fixed` — failed in the baseline, passes in the candidate,
- `regressed` — passed in the baseline, fails in the candidate.

Only then do I aggregate, per slice: overall, critical/noncritical, split and kind.

```python
def compare(cases, baseline, candidate):
    """Pair baseline and candidate scores by case_id and aggregate per slice.
    Every rate uses all cases in the slice as its denominator."""
    result = Comparison([Pair(c, baseline[c["case_id"]], candidate[c["case_id"]]) for c in cases])
    for pair in result.pairs:
        for key in slice_keys(pair.case):
            result.slices.setdefault(key, SliceStats()).add(pair)
    return result
```

### The denominator is a decision

Every rate needs a denominator, and the choice changes the story:

- **All cases in the slice.** Abstaining on an answerable question counts as a failure. This is what the example uses.
- **Only answered cases.** This measures "when it answers, is it right?" and rewards a system that answers less. A candidate that abstains on half the hard questions can improve this number while getting worse for users.
- **Only answerable cases.** Useful for answer quality, but then unanswerable cases need their own metric, or abstention behaviour disappears from the report.

None of these is wrong in general. What is wrong is changing the denominator between runs, or not saying which one is used. The report prints it in the header line of the table.

## The report

With the demo data, the command `.venv/bin/python -m rageval` printed this and exited with code 1:

Look at the `overall` row: 8 of 10 in both runs. Look at the split rows: dev 3 → 3, holdout 5 → 5. A dashboard with only those numbers would say "no change".

The per-case section says something else. The candidate learned to answer a retry question correctly and to ask for clarification on an ambiguous question. At the same time it lost the second half of a multi-hop answer about single sign-on — a critical case — and started inventing a price for a question the documentation cannot answer.

That is why the report lists per-case changes **before** any table, and lists critical cases first among the regressions and among the unchanged failures. A third section lists cases that fail in both runs; here it is empty, but it matters for the gate below. An aggregate is a summary of the cases, not a replacement for them.

## The release gate

The gate turns the comparison into a decision. Its thresholds live in `gate_policy.json`:

```json
{
  "max_critical_failures": 0,
  "max_critical_regressions": 0,
  "max_regressions": 2,
  "max_slice_drop": 0.5,
  "min_slice_size": 3
}
```

These numbers are **illustrative**. They fit a ten-case synthetic example, not every system. What is worth copying is the order of the rules, not the values:

1. **Absolute floor for critical cases.** The candidate may not fail more critical cases than allowed — regardless of the baseline.
2. **Critical regressions.** A critical case that used to pass must not start failing.
3. **Total regressions.** All regressions count here, critical ones included. They are tolerated up to a limit, because some churn is normal when a system changes.
4. **Slice drops.** No slice with at least `min_slice_size` cases may lose more than `max_slice_drop` of its pass rate, measured in absolute points: a slice of four cases that goes from 2 passing to 1 drops by 0.25, not by 50%. Smaller slices are reported but not gated, because one case would swing them completely.

The policy file is validated like the data. Count limits must be integers of at least 0, `max_slice_drop` a finite number between 0 and 1, `min_slice_size` an integer of at least 1. A JSON `true` is not accepted as a count, even though Python treats `True` as 1; before this check, setting both critical limits to `true` turned the demo's failing gate into a pass.

The first rule was not in my first version. While running the finished evaluator, I compared the candidate with itself. The report showed zero regressions and `GATE: PASS` — even though the candidate fails a critical case. A purely relative gate inherits every failure that the baseline already had. If the baseline was bad, "no regressions" just means "equally bad". I added a test for this situation, watched it fail, and then added the absolute rule. Now the candidate compared with itself fails with `critical failures in candidate: 1 > allowed 0`, and the baseline compared with itself passes. A reviewer then pointed out that the report did not say *which* critical case failed: with no change between the runs, it appeared in neither the regressions nor the fixes. That is what the "Unchanged failures" section is for; in this comparison it lists `[CRITICAL] q-sso-plan-role` with its reasons.

What makes a case critical is a product decision, not a technical one. Typical candidates: questions where a wrong answer has legal, financial or security consequences; questions where an invented answer is worse than no answer; questions that represent a large share of real traffic. In the example, the SSO setup question and the HIPAA question are critical; the seat price question is not, even though inventing a price is clearly bad. With a different product, I might decide the other way.

## Running the example

The runnable example is the ZIP archive: [rag-test-set-regression.zip]({{ '/assets/examples/rag-test-set-regression.zip' | relative_url }}). Download and unpack the whole archive; the package contains files such as `rageval/__main__.py` that a static site may not serve individually, so copying single files from the site is not a supported way to run it.

The evaluator uses only the Python 3.11 standard library. pytest is needed only for the tests. The commands below expect a Python 3.11 interpreter that is already installed; `uv venv --python 3.11` looks for it rather than downloading one. Inside the unpacked directory:

```bash
uv venv --python 3.11
uv pip install --python .venv/bin/python -r requirements-dev.txt
.venv/bin/python -m pytest -q -p no:cacheprovider --basetemp=.pytest-tmp
.venv/bin/python -m rageval                                  # exit 1: the gate fails
.venv/bin/python -m rageval --candidate data/baseline.json   # exit 0: the baseline against itself
```

`--basetemp=.pytest-tmp` keeps the files that the tests write inside the project directory instead of pytest's shared temporary directory.

The test suite has 153 tests, most of them parametrised validation cases. They cover malformed JSON, duplicate keys and `NaN`/`Infinity`, integers too large for a float or for Python's 4,300-digit limit, missing and unreadable input files, version mismatches, empty and wrongly typed containers and IDs, missing, extra and duplicate responses, group leakage between splits, abstention in both directions, multi-hop and alternative evidence sets, repeated passage IDs in an evidence set, the case above where fixes and regressions cancel out (8 of 10 in both runs), the type and range of every policy value, each of the four gate rules, the `min_slice_size` boundary, slice drops in absolute points, and the exit codes 0, 1 and 2 of the command line.

The date on this article is an editorial label. The commands and outputs above were executed in October 2026 on macOS (arm64) with uv 0.7.8 and CPython 3.11.12; they were not executed in June 2024.

In 2024 the commands therefore needed CPython 3.11 to be installed first (3.11.0 was released on 24 October 2022). My 2026 run used a newer uv, which can manage interpreters itself; the commands above do not rely on that.
- pytest 8.2.2 was uploaded to PyPI on 4 June 2024. It and its dependencies (iniconfig 2.0.0, packaging 24.0, pluggy 1.5.0) were resolved with `uv pip install --exclude-newer 2024-06-06T07:00:00Z pytest==8.2.2`. uv's resolver ignores files uploaded after that timestamp, so this set was available on PyPI before the article's date. `requirements-dev.txt` pins exactly this set.

## Where this guarantee ends

The report catches regressions **on the cases in the test set**, scored by **these checks**, for **this corpus version**. Each part of that sentence is a limit.

- Ten cases are enough to show the mechanics and far too few to make a decision. Per-slice numbers on one or two cases are noise.
- Fact and citation checks are proxies. Passing them does not prove faithfulness; failing them does not always mean the answer is wrong.
- Stored responses are a snapshot. A model with sampling can produce a different answer on the next run; one run per system cannot tell a regression from variance. For non-deterministic systems I would store several runs and gate on cases that fail consistently.
- The holdout protects against overfitting only as long as I don't make dozens of decisions while looking at it.
- Critical labels and thresholds encode priorities. They should be reviewed like code, not tuned until the gate passes.

What the structure does guarantee is narrower and more useful: the two runs were compared on the same cases, against the same references and the same corpus, and every change in outcome is listed by name. A total that stayed the same can no longer hide the one case that broke.
